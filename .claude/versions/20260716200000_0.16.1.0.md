# Versão 0.16.1.0 — `vercel.json` (rewrite de SPA para o primeiro deploy)

Data: 2026-07-16

Patch nascido do primeiro deploy real na Vercel. Uma linha de configuração e bastante documentação do
que se aprendeu apanhando.

## O problema

A Vercel serve o `dist` como arquivos estáticos. As rotas do client (`/feeds`, `/articles/:id`,
`/auth/callback`) **não existem como arquivo** — só existem dentro do React Router. Sem rewrite,
qualquer acesso direto ou F5 dá 404.

O caso grave não é o F5: é o **`/auth/callback`**. O backend redireciona o navegador para lá ao
voltar do Google, então **sem o rewrite o login nunca completa** — foi exatamente o 404 que o dono
bateu depois de resolver as allowlists.

## A correção

`vercel.json` na raiz:

```json
{
    "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

- Mantido **mínimo de propósito**: `buildCommand`/`outputDirectory`/`framework` não entram porque o
  preset Vite do painel já resolve — duplicar aqui só criaria duas fontes de verdade para divergir.
- O catch-all `/(.*)` não engole os assets: a Vercel checa o **filesystem antes** dos `rewrites`, então
  `/assets/*.js` continua sendo servido como arquivo.

## Documentação (a parte que mais vale)

`PROJECT.md` ganhou a seção **Deploy (Vercel)** com o que custou tempo no primeiro deploy:

- **As três allowlists do login**, que erram em pontos diferentes e são fáceis de confundir:
    1. **Backend valida o callback do SPA** (`OAUTH_ALLOWED_REDIRECT_URIS`) → erro
       `{"error": "invalid redirect_uri"}` vindo da API.
    2. **Google valida o callback do backend** (Google Cloud Console) → `Erro 400:
redirect_uri_mismatch`. **Nada a ver com a Vercel**: quebra quando a API muda de endereço
       (localhost → ngrok/produção). O link "detalhes do erro" mostra a URI exata recebida.
    3. **Backend valida a origem** (`CORS_ALLOWED_ORIGINS`) → `Failed to fetch` em toda chamada
       (parece API fora do ar, mas é CORS).
- **Domínio estável, nunca a URL com hash**: `...-krgq3y3m0-...` muda a cada push. Como o
  `redirect_uri` sai de `window.location.origin` (`AuthService`), navegar pela URL com hash manda a
  URL com hash para a allowlist e reprova. Consequência: **deploys de preview não funcionam**, pois
  ganham domínio novo e as allowlists são exact-match.
- **Variáveis são embutidas em tempo de build** → mudou, tem que redeployar. `VITE_API_URL` precisa do
  `/v1`; se faltar, o build **passa** e o app fica em tela branca (o `config/env.ts` lança em runtime).
  `VITE_DEV_LOGIN_ENABLED` não deve existir em produção.

não existe. Corrigida, com ponteiro para o item de defesa-em-profundidade no ROADMAP → Futuro.

## Verificação

- `npm run build` verde; `format:check`/`lint`/`tsc` limpos; `vercel.json` é JSON válido.
- **Não verificável localmente, e isso é honesto**: `vercel.json` só tem efeito **na Vercel**. O dev
  server do Vite já faz fallback de SPA por conta própria, então rodar local **não prova nada** sobre
  esse arquivo. A confirmação real é o dono dar push e completar o login em produção.

## Como testar (em produção, após o push)

1. Abrir `https://<dominio-estavel>/feeds` direto (sem passar pela home) → deve carregar, não 404.
2. Dar F5 numa notícia (`/articles/:id`) → deve continuar na notícia.
3. Fazer o login com Google de ponta a ponta → o retorno em `/auth/callback` deve processar os tokens
   e cair em `/feeds`. Esse é o teste que importa.
